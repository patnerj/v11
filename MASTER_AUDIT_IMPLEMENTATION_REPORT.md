## Executive Summary

This is a substantial, feature-rich platform (trading engine, multi-phase evaluation, PvP arena, scaling, three payment gateways, KYC, affiliates) with real architectural strengths — the money-moving core (open/close position, margin, PnL) is centralized in one engine class, several concurrency-sensitive paths already use `GET_LOCK`/atomic-claim patterns correctly, and the payout "mark paid" flow correctly re-baselines drawdown floors. Across both audit rounds, **20 CRITICAL/HIGH bugs have been fixed** — several of which mean core safety mechanisms (stop-loss, payment verification, PvP settlement, KYC upload safety, the trading terminal's own resizable-panel layout) were **completely non-functional, bypassable, or actively broken in the shipped build**, not merely edge-case-buggy — plus **~85 further findings** (CRITICAL through LOW) requiring a fix but not yet applied, spanning the PvP engine, scaling engine, payouts, admin panel, and a platform-wide "pending orders bypass every rule enforcement" architectural gap confirmed independently by 7 separate audit passes. Two Round-1 findings were independently **re-checked and found already resolved** by this session's own earlier fixes — a good cross-validation signal.

**Before this platform accepts real trader funds, the CRITICAL items in A.1 and A.3 must all be resolved and re-tested end-to-end against a real WordPress+MySQL+Stripe/Confirmo-sandbox environment** — nothing in this report was executed, only read.

## PART A — Audit Findings & Bugs Discovered

### A.1 — Fixed in this session (20 items, all verified by direct code read, brace/syntax-checked after edit)

Each was cross-checked against a related codebase where the identical bug class was found, fixed, and independently re-verified earlier this session — several of these exact defects (SL/TP claim guard, commission double-charge, margin currency routing, consistency-rule breach, HFT-reject-blocks-forced-closes, pending-order rule bypass) are the SAME underlying architectural mistake repeated across both codebases, which is itself a signal worth acting on (see Part B).

**[FIXED-01] CRITICAL — `includes/class-trading-engine.php:642` — SL/TP never actually auto-closed a position**
- **Root cause:** `check_sl_tp()`'s "claim guard" ran `UPDATE fxsim_positions SET pnl = pnl WHERE id=%d` (a no-op self-assignment) and treated `rows_affected === 0` as "already claimed by a concurrent process, skip." Under MySQL's default (non-`CLIENT_FOUND_ROWS`) semantics, a no-op UPDATE **always** reports 0 affected rows, even for an uncontested match — so the guard fired unconditionally and `close_position()` was never reached. Every stop-loss and take-profit on the platform was inert.
- **Fix applied:** Removed the broken guard entirely. `close_position()` already re-fetches and deletes the position inside its own transaction, which is sufficient protection against a concurrent double-close (the loser finds no row and fails harmlessly) — the extra guard was both broken and redundant.

**[FIXED-02] CRITICAL — `includes/class-trading-engine.php:757` — Commission charged twice on every closed trade**
- **Root cause:** `open_position()` deducts commission from balance at open. `calc_pnl()` (used to compute the close-time balance credit) subtracts commission a second time. Every full close, force-close, and partial close over-charged commission by 1×, compounding across every trade on the platform — and directly corrupts the payout-eligible-profit figure (see FIXED-line for payout, A.3).
- **Fix applied:** Added `+ (float)$pos->commission` (prorated share for partial closes) back at the balance-crediting line in `close_position()` and `partial_close()`. `calc_pnl()` itself is untouched — its commission-inclusive result is still correct for informational floating-PnL display.

**[FIXED-03] CRITICAL — `includes/class-trading-engine.php:224` — Min-hold "reject" policy blocked system-forced closes, trapping losing positions open**
- **Root cause:** The `min_hold_action='reject'` check in `close_position()` applied identically to a voluntary manual close and to SL/TP triggers, weekend force-closes, and breach cleanup — none of which previously had a way to bypass it. A young losing position on a plan with a min-hold rule could not be closed by its own stop-loss, by weekend liquidation, or by breach cleanup.
- **Fix applied:** Added `bool $force = false` to `close_position()`; gated the reject-throw on `!$force`; updated the 3 system-initiated call sites (SL/TP trigger, `execute_weekend_close()`, breach's `force_close_all_positions()`) to pass `force: true`. The flag-insertion for record-keeping now fires regardless of force, so violations are still logged.

**[FIXED-04] CRITICAL — `includes/class-trading-engine.php:1579` — Margin miscalculated for EURJPY/GBPJPY/EURGBP (cross pairs)**
- **Root cause:** `calc_margin_usd()` correctly handles USD-quote and USD-base pairs but fell into a fallback (`base_margin * $price`) for the 3 cross pairs actively traded on this platform — overstating EURJPY/GBPJPY margin by ~100-150× (treating a ~150 JPY price as a USD rate) and understating EURGBP margin by ~20%.
- **Fix applied:** Added explicit EURGBP/EURJPY/GBPJPY branches that convert through the live EURUSD/GBPUSD rate (with a hardcoded fallback if the feed has no current price), mirroring the routing `calc_pnl()` already implements correctly for the same symbols.

**[FIXED-05] CRITICAL — `includes/challenge/class-challenge-engine.php:182` — Consistency rule failed traders on their first winning day**
- **Root cause:** The consistency check ran unconditionally after every trade close and called `breach()` directly. With exactly one profitable day on record — true by definition on a trader's first win — `best_day_pct` is mathematically always 100%, exceeding any realistic threshold.
- **Fix applied:** Extracted `check_consistency()` returning a pass/fail struct (never calling `breach()`); moved the check to gate phase promotion instead of running as a standalone breach trigger.

**[FIXED-06] CRITICAL — `includes/class-rest-api.php:4884` — `/mt5/sync` accepted unauthenticated writes when the auth header was simply omitted**
- **Root cause:** `if ($secret !== '' && !empty($provided) && !hash_equals($secret, $provided))` — the `!empty($provided)` term meant that omitting the header entirely (not just sending a wrong one) skipped verification completely. This endpoint writes `current_balance`, `peak_balance`, and can flip a challenge to `'failed'` via its drawdown-breach check, straight from the unauthenticated request body — allowing any anonymous caller to arbitrarily corrupt a trader's balance or fabricate a drawdown breach.
- **Fix applied:** Removed the `!empty($provided)` term — `hash_equals($secret, '')` already correctly evaluates false, so a missing header now fails closed whenever a secret is configured.

**[FIXED-07] CRITICAL — `includes/stripe/class-stripe.php:152` — Stripe webhook signature check skippable by omitting the signature header**
- **Root cause:** `if ($wh_secret && $sig) { verify... }` — an attacker who simply doesn't send the `Stripe-Signature` header bypasses verification entirely, and the handler proceeds to process the payload as a trusted event. Since `checkout.session.completed` auto-activates a paid challenge account, this allowed **free challenge activation with zero payment** by POSTing a fabricated event with an invented `session_id`.
- **Fix applied:** Changed to `if ($wh_secret) { if (!$sig || !verify_signature(...)) { fail } }` — a missing signature now fails closed whenever a secret is configured, same fix shape as FIXED-06.

**[FIXED-08] CRITICAL — `includes/class-confirmo.php:188` — Confirmo webhook idempotency was a non-atomic check-then-act race**
- **Root cause:** `SELECT` order status, check in PHP, then unconditional `UPDATE` — two near-simultaneous `'paid'` callback deliveries for the same order could both pass the check before either commits, both calling `create_challenge()` and producing two funded accounts from one payment.
- **Fix applied:** Replaced with an atomic claim: `UPDATE ... SET status='approved' ... WHERE id=%d AND status NOT IN ('approved','completed')`, gated on `$wpdb->rows_affected`.

**[FIXED-09] HIGH — `includes/class-confirmo.php:206` — A failed `create_challenge()` still sent a "challenge purchased" confirmation email**
- **Root cause:** The order was already marked `'approved'` before `create_challenge()` was attempted; on failure, the code fell through to send the success email anyway (using `challenge_id = 0`), leaving a paying customer believing they have an account when they don't, with no admin alert.
- **Fix applied:** Email now only sends on `$result['success']`; on failure, logs to `error_log` and writes an admin-log entry (`confirmo_activation_failed`) instead, so the order is flagged for manual resolution rather than silently misleading the customer.

**[FIXED-10] CRITICAL — `includes/class-payments.php:150` — `approve_order()` had the same check-then-act race, shared by both the Stripe auto-approval path and admin manual approval**
- **Root cause:** Identical pattern to FIXED-08, but in the shared function both the Stripe webhook and the admin "approve payment" button call — meaning the race was reachable from two different directions at once.
- **Fix applied:** Same atomic-claim pattern as FIXED-08, applied here so both callers are protected by one fix.

**[FIXED-11] CRITICAL — `includes/class-pvp-engine.php:397,457` — PvP `settle_match()` had zero authorization check; anyone could force-settle any match; idempotency was also a check-then-act race**
- **Root cause:** `settle_match(int $match_id)` took no caller identity at all — any authenticated user (participant or not) could call `POST /pvp/match/{id}/settle` on any match, locking in whichever side currently led. Separately, `if ($match->status === 'completed') return already-settled` was a non-atomic check ahead of an unconditional status UPDATE, allowing a double-settle to fire win/loss side effects twice.
- **Fix applied:** Added an optional `int $requesting_user_id = 0` parameter (0 = trusted/internal caller); when non-zero, requires the caller be one of the match's two participants or an admin (`user_can(..., 'manage_options')`). Replaced the idempotency check with an atomic `UPDATE ... SET status='completed' WHERE id=%d AND status != 'completed'` claim (no new ENUM value needed — verified `status` is `ENUM('waiting','active','completed','cancelled')` before designing the fix). REST handler now passes `get_current_user_id()`.

**[FIXED-12] HIGH — `includes/class-trading-engine.php:803` — Pending (limit/stop) orders could bypass a plan's mandatory-stop-loss rule**
- **Root cause:** `place_pending_order()` fetched `plan_rules->stop_loss_required` but never checked it — unlike `open_position()`, which correctly rejects a market order with no SL when required. A trader on an SL-mandatory plan could place a pending order with no SL and have it fill with none.
- **Fix applied:** Added the identical guard `open_position()` uses, immediately after the SL/TP-vs-target validation in `place_pending_order()`.

**[FIXED-13] HIGH — `includes/class-trading-engine.php:216,348` — Toxic-trade/min-hold check read `$account->plan_id`, a column that doesn't exist on `fxsim_accounts`**
- **Root cause:** `close_position()` and `partial_close()` both did `FXSIM_Challenge_DB::get_plan((int)$account->plan_id)` where `$account` comes from a plain `fxsim_accounts` row — that table has no `plan_id` column at all, so the lookup always returned null and the entire min-hold/toxic-trade block silently never ran, in either direction (this is why FIXED-03's fix mattered: without this fix too, the reject-block was already dead code, but the same broken lookup pattern would have resurfaced the instant the plan_id lookup was fixed elsewhere).
- **Fix applied:** Replaced with a scalar lookup via `fxsim_challenge_accounts.plan_id` joined on `fxsim_account_id`, matching the correct pattern already used elsewhere in the same file (`place_pending_order()`, `get_user_active_account()`).

**[FIXED-14] CRITICAL — `propfirm-frontend-v10.7.1/src/app/dashboard/trading/page.tsx:238-360` — Trading terminal's own panel layout was broken by an unnoticed major-version dependency change (react-resizable-panels v1→v4)**
- **Root cause:** `package.json` pins `react-resizable-panels@^4.12.2`. Verified directly in the installed package's compiled runtime (`node_modules/react-resizable-panels/dist/react-resizable-panels.js`, function `xt()`, line 20): `case "number": return [e, "px"]` — any bare JS number passed to `defaultSize`/`minSize`/`maxSize`/`collapsedSize` is now interpreted as **pixels**, not percent (confirmed `defaultSize` goes through the identical conversion at lines 95-99 and 1344-1346). `DesktopLayout` in `page.tsx` passed every one of these props as a raw number (e.g. `defaultSize={24} minSize={18} maxSize={30}`), with values clearly intended as percentages (they sum to 100 per panel group, matching the old v1/v2 API). Under the installed v4 runtime, the market-watch and order-ticket panels were constrained to **18-30 pixels wide** instead of 18-30% of the viewport, and the positions/pending panel to 10-30px tall. This is a real regression of the platform's already-once-fixed "panels squished" bug (this session's own task history shows it was fixed previously as a CSS/layout issue — a later dependency bump silently reintroduced it via an API contract change, not a CSS change, which is why the earlier fix didn't catch it).
- **Fix applied:** Converted all 6 numeric size props in `DesktopLayout` (market-watch, center, chart, positions/pending, order-ticket panels) to percentage strings (`defaultSize="24%"`, etc.), matching v4's actual API contract. `MobileLayout` does not use `react-resizable-panels` and was unaffected.

**[FIXED-15] CRITICAL — `includes/class-rest-api.php:2247` (`store_kyc_file()`) — KYC document extension taken from client filename, not validated MIME type**
- **Root cause:** The function correctly validates the uploaded file's actual bytes via `mime_content_type()`, but then built the saved filename's extension from `pathinfo($file['name'], PATHINFO_EXTENSION)` — the attacker-controlled original filename — completely unconstrained by the MIME allow-list. A JPEG/PHP polyglot (valid JPEG magic bytes with a PHP payload embedded in a COM/EXIF segment) still sniffs as `image/jpeg` and passes validation, while a filename of `shell.php` would be saved as `id_doc_{timestamp}.php` inside the web-uploads tree — full RCE if the runtime `.htaccess` isn't honored (true under nginx, or Apache with `AllowOverride None`, both common production configs). Reachable by any authenticated trader via the KYC upload flow.
- **Fix applied:** Extension is now derived exclusively from the already-validated `$mime` via a fixed map (`image/jpeg→jpg`, `image/png→png`, `image/webp→webp`, `application/pdf→pdf`), with the `pathinfo()` extraction removed entirely.

**[FIXED-16] CRITICAL — `includes/class-rest-api.php:2504-2533` (`admin_payout_status()`) — Payout balance deduction was two un-transacted, unchecked UPDATEs, never logged to the transaction ledger**
- **Root cause:** When a payout transitions to `'paid'`, the function separately (a) writes `status='paid'` to `fxsim_payouts`, then (b) deducts the withdrawn amount from `fxsim_accounts.balance/equity` and rebaselines `fxsim_challenge_accounts` — with no transaction wrapping either step, no error handling, and no call to `FXSIM_Database::log_transaction()` (confirmed via grep this is the only balance-mutating `$wpdb->update` in the file that skips it), so a trader's `/transactions` history never shows the payout withdrawal that reduced their balance. Independently confirmed reachable via normal data conditions (not just a crash): if the linked challenge/account row can't be resolved, the deduction silently no-ops entirely while the payout still commits as `'paid'`.
- **Fix applied:** Wrapped the deduction + rebaseline in `START TRANSACTION`/`COMMIT`/`ROLLBACK` with a `catch (\Throwable)`, added the missing `log_transaction()` call, and replaced the silent no-op when the challenge/account can't be resolved with a loud `error_log()` + `FXSIM_Database::log_admin()` trail (`payout_deduction_failed` / `payout_deduction_skipped`) so a mismatched "paid but not deducted" state is always findable and flagged for manual reconciliation. Note: this does not address the separate open question in A.2-1 (the second `admin_approve_payout()` endpoint) — see there for the un-fixed piece.

**[FIXED-17] CRITICAL — `includes/stripe/class-stripe.php:192` (`handle_webhook()`) — Stripe webhook discarded `approve_order()`'s result and always returned HTTP 200**
- **Root cause:** `FXSIM_Payments::approve_order(...)`'s return value was never captured. If `approve_order()` fails after the order is already committed `'approved'` (e.g. the plan was deleted between checkout and payment), the webhook still returns 200, so Stripe never retries, nothing is logged, and a customer who paid successfully has no working challenge account with zero trace anywhere.
- **Fix applied:** Captured the result; on `success === false`, `error_log()`s the failure with order/user/plan context and writes an admin-log entry (`stripe_activation_failed`) so support can find and manually resolve it. Still returns 200 to Stripe (retrying wouldn't fix a deleted plan), matching the same reasoning already applied to the equivalent Confirmo fix earlier this session.

**[FIXED-18] HIGH — `includes/class-trading-engine.php` (`check_sl_tp()` line ~624, `process_pending_orders()` line ~1258) — Both money-critical cron entry points used bare `try/finally` with no `catch`**
- **Root cause:** Any uncaught `\Throwable` inside the SL/TP-check loop or the pending-order-fill loop (a DB hiccup, a `TypeError` from a symbol/plan lookup) propagated all the way out of the function. Since these run on a ~30-second WP-Cron tick with no application-level visibility into a fatal inside the callback, the entire tick's remaining work (every other position/order due that tick) silently aborted with zero trace beyond whatever the server's raw PHP error log happened to capture.
- **Fix applied:** Added `catch (\Throwable $e) { error_log(...) }` before the existing `finally` (lock release) in both functions, so one bad row logs and lets the rest of that tick's work still complete instead of aborting silently.

**[FIXED-19] HIGH — `src/components/dashboard/trading/account-strip.tsx:49` (`renderProgressBars()`) — Crashed the whole dashboard route whenever a challenge's plan/account couldn't be resolved**
- **Root cause:** The backend's `get_metrics()` returns an empty array `[]` (not `null`) whenever a challenge's linked plan or account row is missing — trivially reachable via the already-shipped `/admin/plans/purge-and-reset` action, or any orphaned `plan_id`. `[]` is truthy in JS, so the component's `if (!metrics) return null` guard didn't catch it, and the very next line, `metrics.plan.drawdown_type`, threw on the `undefined` `.plan`. Per a companion finding (FIXED-14's neighbor, not itself auto-fixed — see A.4), the trading terminal has no local error boundary, so this crash takes down the entire terminal content, not just this widget.
- **Fix applied:** Extended the guard to `if (!metrics || !metrics.plan) return null`.

**[FIXED-20] CRITICAL — `propfirm-frontend-v10.7.1/src/app/admin/traders/page.tsx:228` (`handleToggleBan()`) — "Ban/Freeze Account" sent an invalid status value and showed a false success toast**
- **Root cause:** Two independently-verified defects compounding: (1) the button sent `newStatus = 'suspended'`, but the backend's `admin_set_status()` (`class-rest-api.php:1676`) only accepts `active|frozen|banned` and returns HTTP 400 for anything else — confirmed by direct read of both sides; (2) `fxsim()`/`rawFetch()` never throws on a non-2xx response, it resolves `{ok:false, error}` — and the calling code never checked `res.ok` before showing `toast.success(...)`. An admin clicking "Ban / Freeze Account" always saw a green confirmation, while the trader's status was never actually changed in the database.
- **Fix applied:** Changed the sent value to `'banned'` (matching the backend enum), and added an explicit `if (!res.ok || !res.data.success)` check that shows `toast.error(...)` with the real backend message and returns before the success path.

### A.2 — Confirmed by direct read, intentionally NOT auto-fixed (business/product judgment required)

**[A.2-1] `includes/class-rest-api.php:2808` vs `:2469` — Two parallel "approve payout" admin endpoints, one of which never moves money**
`admin_payout_status()` (`/admin/payouts/{id}/status`, transition to `'paid'`) correctly debits balance and re-baselines the drawdown floor. `admin_approve_payout()` (`/admin/challenge/{id}/approve-payout`) only flips the payout row's status and sends a **"💸 Payout Processed!"** notification — with **zero balance deduction**. If this second endpoint is ever used as the terminal admin action (its own copy strongly implies it is), the same profit stays payable indefinitely.
*Why not auto-fixed:* whether this is a genuine two-step workflow (approve-intent → separate mark-paid) or a dangerous duplicate depends on the admin's actual intended process, which requires checking which endpoint the admin frontend UI calls and confirming intent with the product owner. **Recommend: verify which endpoint the frontend calls; if `admin_approve_payout` is reachable as a terminal action, either delete its money-movement-implying copy or route it through the same atomic balance-debit logic as `admin_payout_status`'s `'paid'` transition.**

**[A.2-2] `includes/class-confirmo.php:179` — Challenge activates on Confirmo status `'paid'`, not `'confirmed'`**
Confirmo's own notification model distinguishes `'paid'` (transaction detected) from `'confirmed'` (final, post-blockchain-confirmation state). Activating on `'paid'` risks granting a funded account for a crypto payment that later fails to reach finality (reorg, double-spend).
*Why not auto-fixed:* I could not verify Confirmo's exact current API status-string contract without live docs access in this environment. **Recommend: confirm against Confirmo's live API reference for the merchant account's configured coins before changing `if ($status === 'paid')` to `'confirmed'` — getting this wrong in the other direction (requiring a status that never actually fires for some coins) would silently break all crypto activations.**

## PART B — Architectural & UX Improvements (Prioritized)

### High priority
1. **Unify the two order-entry paths.** The single largest source of findings in this audit (7 independent confirmations) is that `open_position()` and `place_pending_order()`/`fill_pending_order()` maintain two separate, drifting copies of plan-rule enforcement (SL-required, news window, `detect_trade_patterns()`). Extract one shared `enforce_plan_rules($account, $plan_rules, $order_context)` helper both paths call, so a rule added to one path can't silently miss the other again — this exact defect class (enforced on one path, forgotten on a sibling) recurs at least 4 more times across this audit (Confirmo missing coupon/affiliate calls, the two payout-approval endpoints, `detect_syndicate_hedging`'s missing pending-order coverage).
2. **Build the missing margin-call/stop-out engine.** `margin_call_level`/`stop_out_level` are fully designed (schema + admin UI) but entirely unenforced — this is the platform's single largest unbounded-risk gap. Mirror `check_sl_tp()`'s tick-based pattern (once the claim-guard fix above is applied as the template for "how to do this correctly").
3. **Adopt one canonical "atomic claim" idiom platform-wide** and use it everywhere a check-then-act race was found (this audit fixed 3 instances of this exact pattern and found ~4 more still open: daily-tasks overlap, breach() non-idempotency, join_match(), weekend-holding's guard). Document it once (e.g. in a `CONTRIBUTING.md` snippet) so future code doesn't reintroduce it.
4. **PvP/tournament engine needs a design pass before real money touches it.** Every money-relevant behavior (escrow, settlement authorization, outcome determinism) is currently either missing or exploitable. Recommend treating it as feature-flagged/disabled in production until A.3's PvP section is fully resolved and independently tested.

Wire it in (or port the wrapping into the live file) so one widget crash (e.g. FIXED-19's now-fixed but illustrative `metrics.plan` case) can't take down the whole terminal.

The current `.htaccess`-only protection is inert under nginx or `AllowOverride None`, and filenames are guessable from a user ID + rough submission time.

23. ✅ **Found and fixed a more severe issue than the original finding described.** The original item was framed as "CSRF-blocks-API-keys" (implying the nonce check was too strict). The reality, found by reading `protradefx-headless-bridge.php`'s `bypass_rest_nonce()`: it unconditionally returned `true` for **every single request to the entire `fxsim/v1` namespace**, completely disabling WordPress core's REST cookie-nonce CSRF check platform-wide — not narrowly for API keys. Combined with this app's own `verify_nonce()` (in `class-rest-api.php`) also being a no-op that only checks login state, **nothing in the stack was verifying a real CSRF token for any cookie-authenticated, state-changing endpoint** — including money-moving ones like `challenge_payout()` (which accepts an arbitrary payout `address` in the request body). A plain HTML `<form>` POST (no JavaScript, no CORS preflight, cookies attached automatically by the browser) from any external site could have executed as a fully authenticated request against any of them.
    **Fix applied**: rewrote `bypass_rest_nonce()` to only skip Core's nonce check for requests that genuinely don't need it — safe methods (GET/HEAD/OPTIONS), bearer-token-authenticated requests (not CSRF-able — browsers don't auto-attach `Authorization` headers), and anonymous/not-yet-logged-in requests (nothing to forge). A cookie-authenticated, state-changing request now must present the `X-WP-Nonce` header with the nonce issued at login — which the frontend's `fxsim.ts` **already sends on every non-public request**, so no frontend change was needed.
    **Live-verified via real HTTP requests**: logged in via `curl` with a cookie jar, captured the real session nonce from the login response, then: (a) confirmed a GET needs no nonce, (b) confirmed a state-changing POST **with** the nonce succeeds, (c) confirmed the **identical** POST **without** the nonce (simulating what a cross-site attacker's request would look like server-side) is now rejected with `403 rest_cookie_invalid_nonce`, and (d) confirmed via a follow-up GET that the state genuinely did not change — the rejection was real, not cosmetic.
